# AI Reviewer — 记忆强化与自我学习方向分析

> 生成日期：2026-06-23

---

## 一、当前架构的核心约束

本项目是一个 **无状态的 GitHub Action**，每次 PR 事件触发后执行完即退出。唯一的"记忆"机制是把审查状态（rawSummary、commitId 等）写进 PR 评论的隐藏块里，下次触发时再读取。

这带来两个根本性缺陷：

| 缺陷 | 表现 |
|------|------|
| 跨 PR 无记忆 | 同一个反模式在 PR #100 审查过，PR #200 里仍从零开始 |
| 无反馈信号 | 开发者接受/拒绝了哪条 AI 评论，bot 完全不知道 |

---

## 二、四个可落地的方向

### 方向 1：RAG — 历史 Review 知识库

**核心价值：** 让每次审查不再从零开始，而是站在历史经验上。

**工作原理：**

```
新 PR diff (patch)
    ↓ embedding
向量检索 (Pinecone / Qdrant)
    ↓ top-k 相似历史 review 片段
"这类模式在 PR #45 里曾发现 SQL 注入风险"
    ↓ 注入 review prompt
heavyBot → 更精准、更一致的审查
```

**实现路径：**
1. 每次审查完成后，将 `(patch_embedding, review_finding)` 写入向量库
2. 新 PR 审查前，用当前 patch 检索 top-k 相似历史记录
3. 将检索结果作为额外上下文拼入 `reviewFileDiff` prompt

**存储选型：**
- 推荐 Pinecone Serverless 或 Qdrant Cloud（成本低，GitHub Action 冷启动可快速连接）
- 索引 key：`{repo}/{file_path}/{patch_hash}`

**扩展点：** `src/review.ts` 阶段四（逐文件代码审查）前注入检索步骤

---

### 方向 2：反馈信号闭环（真正的"自学习"）

**核心价值：** 让 bot 知道哪些评论有价值，哪些是噪音，并随时间自我优化。

**工作原理：**

```
AI 评论 → 开发者 resolve   → 信号: 有效
AI 评论 → 开发者 dismiss   → 信号: 噪音

累积信号
    ↓
动态调整 system_message prompt
    ↓
对"低采纳率"审查类型降权
对"高采纳率"审查类型加权
```

**实现路径：**
1. 监听 `pull_request_review_comment` 的 `resolved` / `dismissed` 事件
2. 记录 `(comment_category, action, repo)` 到外部存储（可复用方向 1 的存储）
3. 定期（如每周）聚合统计，生成各类审查的采纳率报告
4. 将采纳率报告注入 `system_message` 或动态调整 prompt 权重

**扩展点：** `src/review-comment.ts` + `src/commenter.ts` 已有评论事件处理，扩展相对清晰

**数据结构示例：**
```json
{
  "repo": "org/repo",
  "category": "security",
  "sub_type": "sql_injection",
  "accepted": 12,
  "dismissed": 2,
  "acceptance_rate": 0.857
}
```

---

### 方向 3：Repo 代码库 RAG（减少"只见树木不见森林"）

**核心价值：** 让 bot 能感知整个 codebase，而不仅仅是当前 diff。

**当前问题：** bot 只看 diff，看不到全局。常见误判：
- 认为某函数缺失，实则已在其他文件实现
- 无法发现重复代码
- 无法检测与现有约定的冲突

**工作原理：**

```
Repo 全量文件
    ↓ 增量 embedding（仅处理变更文件）
语义代码索引
    ↓ 审查时检索相关上下文
"这个函数在 utils/auth.ts:42 已有类似实现"
"这个错误处理模式与 services/payment.ts 不一致"
```

**扩展点：** 项目已有 `src/dependency-analyzer.ts` 和 `src/repo-tree.ts`，是天然的扩展基础。可在静态导入分析之上叠加语义相似度检索。

**注意事项：**
- 大型 repo 首次索引成本较高，需设计增量更新机制（仅对变更文件重新 embedding）
- Token 预算压力：检索结果需做截断，避免超出 context window

---

### 方向 4：团队约定学习（Convention Extractor）

**核心价值：** 自动感知每个 repo 的隐式编码约定，让审查更贴合团队文化。

**工作原理：**

```
已合并 PR 批量分析
    ↓
提取隐式约定
（命名风格、错误处理、注释规范、测试覆盖要求...）
    ↓
生成动态 team_conventions.md
    ↓
注入每次 review 的 system_message
```

**相比硬写 system_message 的优势：**
- 随项目演化自动更新
- 不依赖人工维护
- 可发现隐式约定（团队约定俗成但从未文档化的规则）

**实现方式：** 可以是一个独立的"约定提取" Action，定期（如每月）运行，产出一份 JSON/Markdown 配置文件提交到 repo。

---

## 三、优先级建议

| 优先级 | 方向 | 理由 |
|--------|------|------|
| P0 | **方向 2（反馈闭环）** | 工程量最小，收益最快，是其他方向的数据基础 |
| P1 | **方向 1（历史 Review RAG）** | 核心记忆能力，需外部存储，但价值最高 |
| P2 | **方向 3（Repo 代码库 RAG）** | 依赖增量索引方案设计，成本可控 |
| P3 | **方向 4（约定学习）** | 锦上添花，依赖前两个方向积累的数据 |

## 四、整体架构演进图

```
当前架构（无状态）
┌─────────────────────────────────────┐
│  GitHub Action 触发                  │
│  → 读取 PR diff                     │
│  → lightBot 摘要 + heavyBot 审查     │
│  → 写评论（含隐藏状态）              │
│  → 退出                             │
└─────────────────────────────────────┘

目标架构（有记忆 + 自学习）
┌─────────────────────────────────────────────────────────┐
│  GitHub Action 触发                                      │
│                                                         │
│  ┌─ 记忆检索层 ──────────────────────────────────────┐  │
│  │  向量库检索：历史相似 patch → 历史 findings        │  │
│  │  约定库读取：team_conventions（方向 4 产出）       │  │
│  └────────────────────────────────────────────────────┘  │
│                ↓ 注入 prompt 上下文                      │
│  ┌─ 审查引擎（当前四阶段流程）──────────────────────┐  │
│  │  lightBot 摘要 → heavyBot 深度审查               │  │
│  └────────────────────────────────────────────────────┘  │
│                ↓ 写评论                                  │
│  ┌─ 反馈记录层 ──────────────────────────────────────┐  │
│  │  评论 ID → 写入跟踪表                             │  │
│  │  resolve/dismiss 事件 → 更新采纳率统计            │  │
│  └────────────────────────────────────────────────────┘  │
│                ↓ 异步更新                                │
│  ┌─ 持久化存储 ──────────────────────────────────────┐  │
│  │  向量库 (Pinecone / Qdrant)                       │  │
│  │  采纳率统计表                                     │  │
│  │  Repo 代码语义索引                                │  │
│  └────────────────────────────────────────────────────┘  │
└─────────────────────────────────────────────────────────┘
```

## 五、关键技术选型参考

| 组件 | 推荐选项 | 说明 |
|------|----------|------|
| 向量库 | Pinecone Serverless / Qdrant Cloud | 无服务器，冷启动友好 |
| Embedding 模型 | `text-embedding-3-small` | 成本低，code 场景效果够用 |
| 元数据存储 | Supabase / PlanetScale | 采纳率统计等结构化数据 |
| 增量索引触发 | GitHub Actions + push 事件 | 仅对变更文件重新 embedding |
